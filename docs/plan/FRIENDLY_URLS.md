# Friendly, shareable URLs (lane URLS)

Operator request: the address bar should be a link a person can read and share, everywhere someone would copy it. A card is `/tasks/KAN-1`, a board `/tasks/KAN`, a note `/notes/engineering/release-checklist-3f9x2ab01k`; old UUID links keep working and turn into the friendly form in place.

Decisions **D770–D789**. Threats **T490–T492**. Migration **083** (`short_ids`; 084 is unused and stays free for this lane's follow-ups). HTTP contract: docs/plan/API_CONTRACTS.md § "Friendly URLs: GET /api/links/:kind/:ref". Builds on lane KEYS (docs/plan/TASK_KEYS.md, D710–D716).

## Shared mechanism

| Piece | Where | What it does |
| --- | --- | --- |
| Slug and short id helpers | `shared/friendlyUrls.ts` | `slugify`, `slugSegment`, `newShortId`, `isShortId`, `shortIdOfSegment`, `itemPath`, `LINK_KINDS` |
| `short_id` column, unique index, insert trigger | `server/migrations/083_short_ids.ts` | on `notes`, `documents` (Files and whiteboards), `collections`, `reports` |
| Link builders and the generic resolver | `server/friendlyLinks.ts` | `cardPath`, `boardPath`, `sprintsPath`, `notePath`, `documentPath`, `whiteboardPath`, `collectionPath`, `collectionRowPath`, `reportPath`; `GET /api/links/:kind/:ref` |
| Name registry | `src/routeNames.ts` | what the tab learned (short id + slug per item, board codes, card keys), read by `formatRoute`/`parseRoute` |
| Router | `src/router.ts` | every friendly shape, the `pending` link, `formatRoute` from the registry |
| Resolution and canonicalization | `src/friendlyLinks.ts`, `src/FriendlyLinkGate.tsx` | resolve a pending link, replace the entry with the canonical URL |

## Decisions

| # | Decision | Why |
| --- | --- | --- |
| D770 | **Ids stay the identity; URLs are a view of them.** Routes keep holding UUIDs. `formatRoute` writes the friendly form when the tab knows the item's name and the UUID form otherwise; `parseRoute` reads both. Every UUID URL the app ever wrote keeps working forever (mail, notifications, Inbox targets, bookmarks). | Nothing outside the router changes meaning; a friendly URL can never break a deep link that already exists. |
| D771 | **Short ids**: 10 characters, lowercase base36, the **first a digit** (`3f9x2ab01k`; 10 × 36⁹ ≈ 10¹⁵). Random (CSPRNG in JS, SQLite `random()` in the trigger), stored in `short_id` with a unique index per table, never reused or changed (a rename, a move, a Bin restore keep it). The leading digit tells a short id from a word, so `/notes/objectives` is never read as one. | Short enough to read and type, long enough that guessing one is pointless (and harmless, T490). A stored random id, unlike a hash of the UUID, can never be reversed into it. |
| D772 | **Slugs** (`slugify`): lower case; accents folded (NFKD, combining marks dropped: Café → cafe); a few letters NFKD keeps transliterated (ß → ss, æ → ae, œ → oe, ø → o, ł → l, đ/ð → d, þ → th, & → and); anything else, other scripts and emoji included, becomes a dash, consistently; runs of dashes collapse, none at either end; at most 60 characters, cut at a dash when one is in the second half. A title that slugs to nothing gives `untitled-<shortid>`. The slug is the title **people see**: a blank note's stored title is "New note", so its URL is `new-note-<shortid>`; a whiteboard drops its stored `.excalidraw` suffix. | Readable and safe in every context (only `[a-z0-9-]`). Dropping non-Latin scripts keeps URLs ASCII; the short id still identifies the item, so nothing is lost. |
| D773 | **Slugs are cosmetic; the short id is authoritative.** A segment is read by its trailing `-<shortid>` (or a bare short id); the slug before it may be stale, wrong, or missing, and a note's folder segment may be anything or absent. A URL whose short id, board code, or card key the tab has not learned yet parses to a route with **`pending: { kind, ref, url }`** and no id; `formatRoute` writes `url` back unchanged (so nothing that rewrites the entry before the app resolves it loses the rest of the path), and the app resolves it. | One rule for every module; the route type says "not resolved yet" instead of guessing. |
| D774 | **Canonical URL in place.** When the registry learns a name (a list or item load, a rename, a move, a code change), the address bar is replaced with the current route's canonical URL if it differs: `history.replaceState`, keeping the entry's state, never a new entry. Resolving a pending link replaces its entry the same way. So a UUID link, a stale slug, a renamed note or folder, a moved card, and a former board code all end on the current URL, and Back never lands on the old form. A query the app's URLs do not own and the fragment are kept. Checks that a path is one the router writes (a notification's href) run with the names suspended (`withoutRouteNames`), so UUID and friendly hrefs both pass as written. | Copying the address bar always gives the current link; history stays exactly as deep as before. |
| D775 | **One resolver**, `GET /api/links/:kind/:ref` (`note`, `file`, `whiteboard`, `collection`, `report`, `board`): `{ id, title }` (`{ id, code }` for a board) when the caller can read the item now; otherwise 404 `{"error":"Not found"}` with the identical body for unknown, binned, unreadable, or malformed. Card keys keep their own lookup, `GET /api/tasks/keys/:key` (D713), which already follows moves and code changes. | No per-module lookup endpoints; the access check is each module's own read check (`readableNote`, `readableDocumentSummary`, `readableWhiteboard`, `readableCollection`, `readableReport`, `readableBoard`). |
| D776 | **Notes**: `/notes/<folder-slug>/<title-slug>-<shortid>`; a note in no folder, or in a folder its reader cannot see, is `/notes/<title-slug>-<shortid>`. The folder segment is the folder the **reader** sees the note in (the list's `folder_id` is already null for a hidden folder). Server-written links (mail, MCP, Inbox) never carry the folder: the server cannot know which folders the reader sees, and a folder's name is not the note's to share; the app adds it when it may. Notes resolve pending links from the loaded list (`resolveNotesRoute`, by `short_id`), so a note the reader cannot read is "Note not found" like an unknown id. Folder lists keep `/notes/folder/<uuid>` and `/notes/shared`. | The requested shape; the folder adds context only for people who can see it. |
| D777 | **Files and whiteboards**: `/files/<name-slug>-<shortid>` (the extension is part of the name: `q3-report-pdf-…`) and `/whiteboards/<name-slug>-<shortid>`; both use `documents.short_id`. No folder segment (Files folders are often private; the item is what is shared). **Collections**: `/collections/<name-slug>-<shortid>`, with views and rows below it by id (`/view/<uuid>`, `/row/<uuid>`). **Reports**: `/reports/<title-slug>-<shortid>` with the page's parameter query (D489) unchanged. List views (`/files/shared`, `/reports/favorites`, folders, report lists) keep their URLs. These apps wait in `FriendlyLinkGate` while a pending link resolves, then mount on the canonical URL; a miss is "… not found" and the app's list. | The entities people share most, after cards and notes. |
| D778 | **Report pages** are recognised by `locationUrl` in either form (`/reports/<uuid>` or `/reports/<segment>`, never the list words), so their parameter query keeps working. | |
| D779 | **Rows and views stay ids** under the friendly collection. | A row has no single title field (its "title" is whichever field the schema puts first), and a view is a sub-page of its collection. |
| D780 | **Server-written links are friendly**: mail (`server/mail/links.ts` `paths.card/board/sprints/note/file/collection`), Inbox targets and result refs (`server/inbox/kinds.ts`, `noteDraftProposals.ts`), and MCP tool `url`s (notes, whiteboards, collections and rows, reports). Each builder falls back to the UUID form for a row without a code or short id (a mail preview's sample ids). The bell's access notices keep id-only hrefs (T68: `public/sw.js` lists their shapes and a bell link never carries a title; `server/mail/links.ts` `idPaths`); the app canonicalizes them when opened. Calendar feeds and Today items carry no item URLs today. Content stays id-based: whiteboard embeds in notes and links inside whiteboards keep `/whiteboards/<uuid>` (a title in content would go stale). | People share what they were sent. |
| D781 | **Tasks** (extends D713): a board's canonical URL is `/tasks/<CODE>` (its sprints `/tasks/<CODE>/sprints`, a saved view `/tasks/<CODE>/views/<v>`); a card's is `/tasks/<KEY>` and its full page `/tasks/<KEY>/full`, both with the board's non-default query (`?view=table`) so closing the card returns to the same view; under a saved view a card stays below the view, `/tasks/<CODE>/views/<v>/card/<KEY>`. The long form `/tasks/<uuid>/card/<uuid>` and board UUIDs still work and canonicalize. Codes and keys are read in any case; a former code (D714) or a moved card's old key (D715) opens the current one and the URL becomes the current one. `/tasks/my` and `/tasks/views` stay the home segments (matched in lower case first; a board coded MY or VIEWS is `/tasks/MY`). A card the tab has no key for (no code, an older server) keeps the long form. The board payload, the board list, and a card read teach the registry codes and keys. | The requested shape; the short link that already existed is now also what the address bar shows. |
| D782 | **Kept opaque on purpose** (titles would leak sensitive information, or there is nothing to share): Vault vaults, environments, and secrets; agent chats and the agent Audit log; calendar events (titles are often personal: appointments, 1:1s); Inbox proposals; Team members, groups, and integrations (names are personal data); Settings → Agents and Knowledge pages; public chat shares (`/share/c/<token>`: the token is the capability). | A slug is read by anyone the URL reaches (T492); none of these is shared by link inside the workspace. |
| D783 | **Not persisted.** The registry lives in memory and is cleared on sign-out and on a change of account; a reload starts empty and resolves friendly URLs again. | No titles in storage. |
| D784 | **Request log**: an app page (anything outside `/api` and `/mcp`) is logged as its first segment only (`/notes/:path`), at whatever level; API paths keep their route templates (`/api/links/:kind/:ref`). | T491. |
| D785–D789 | Reserved for this lane's follow-ups. | |

## Threats

- **T490 — Resolving as an existence or title oracle.** Short ids are random (10¹⁵ space) and board codes guessable; a resolver that answered differently for an item the caller cannot read would reveal that it exists or its title. Every miss is the same 404 body (a test compares bodies); the title is read only after the module's own read check; Notes resolve from the reader's own list; card keys keep T460's rules. A short id is not a capability: knowing one grants nothing.
- **T491 — Titles in logs.** Friendly URLs carry titles, folder names, board codes, and card keys. The request log writes an app page as its first segment only (D784); API routes log their templates, so `/api/links/:kind/:ref` never logs the ref. Audit logs never held paths.
- **T492 — Titles in history, Referer, and shared links.** A friendly URL puts the item's title in browser history, bookmarks, and anything the link is pasted into. `Referrer-Policy: no-referrer` (server/index.ts, and on file responses) keeps it from other sites. A person sharing a link shares the title, which every reader of the item sees anyway; entities whose titles are sensitive stay opaque (D782). Server-written note links never carry a folder name (D776). Slugs are only `[a-z0-9-]`, so they cannot inject markup or a path into mail links (T223 holds).

## Tests

`tests/friendlyUrls.test.ts`: slugify (accents, transliteration, other scripts, emoji, length cut, empty), short id format and uniqueness over 20,000, segment parsing (stale slug, any case, bare id, words and UUIDs never), migration 083 (backfill unique over binned rows, idempotent re-run, the trigger per row of a multi-row insert, the unique index and CHECK), the resolver for notes, whiteboards, collections, boards (stale slug, upper case, former code) and access-denied ≡ unknown ≡ malformed ≡ binned (identical bodies, no title), the server link builders and their UUID fallbacks, and the request log template. `tests/friendlyRouter.test.ts`: format/parse round trips for every new shape (notes with and without a folder, untitled, files, whiteboards, collections with views and rows, reports with parameters, boards, sprints, saved views, cards as dialog, page, with a query, and under a saved view), stale slugs and UUID links, renamed notes and folders, a moved card's old key, a former board code, pending links (formatted unchanged, upper-case keys), Notes resolving a pending link from its list (and not-found), the notification href check, and the canonicalizer (replaceState with the entry's state, query and fragment kept, pending and other apps untouched).

## Follow-ups (exact steps)

1. **Folder URLs** (`/notes/folder/<uuid>`, `/files/folder/<uuid>`, `/whiteboards/folder/<uuid>`): add `short_id` to `folders` in a new migration (084 is free) with the same backfill and trigger as 083; add `"folder"` to `LINK_KINDS` and to `resolveLinkRef` (check with `listReadableFolders`); in `parseCollection` read `folder/<slug>-<shortid>`; in `formatCollection` write it from a `nameItems("folder", …)` registration in `loadNavigation` and the Files/Whiteboards folder loads.
2. **Report folders and lists** (`/reports/folder/:id`, `/reports/lists/:id`): `short_id` on `report_folders` and `report_lists` (migration 084), `report-folder`/`report-list` kinds checked with `liveFolder` and `readableList`, and the two branches in `parseRoute`'s reports block.
3. **Cross-board task views** (`/tasks/views/:id`): `short_id` on `task_views`; parse in `parseTasksHome` (a segment with a short id); name views from `homeApi` list loads.
4. **Notes beyond the list's 500**: `resolveNotesRoute` finds pending notes only in the loaded list (as UUID links did); call `resolvePending` on a miss and reload the note by id.
5. **Links inside content**: accept friendly paths in `shared/whiteboardScene.ts` `nookPathPattern` (links pasted into whiteboards) once the canvas can resolve them.
