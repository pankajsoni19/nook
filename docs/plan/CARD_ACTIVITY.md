# Card activity history (lane ACTIVITY)

A card's history ("Shubhangi moved this from **To do** to **Done** · 10 days ago"), shown interleaved with its comments in the card dialog and the full-page card. Decisions **D740–D746**, migration **067**. Contract: [API_CONTRACTS.md § Card activity](API_CONTRACTS.md#card-activity-lane-activity-d740d746-migration-067).

- **D740 — One table, display snapshots.** `card_activity` (id, card_id, board_id, actor_id, actor_label, via, kind, payload, created_at). Payloads keep ids plus the label at the time (`ActivityValue`), so history reads the same after a tag is deleted or a column renamed. `board_id` is the board when it happened and has no foreign key (a card that later moves boards keeps its history). Ids are time-ordered (UUIDv7), so entries written in one transaction keep their order.
- **D741 — Table-driven kinds; the extension point.** `shared/cardActivity.ts` lists the kinds (`CARD_ACTIVITY_KINDS`: shape `change` / `item` / `event`, and whether it coalesces); `src/tasks/cardActivity.tsx` has one renderer per kind (`ACTIVITY_RENDERERS`, typed `Record<CardActivityKind, …>`, so a kind cannot be listed and not drawn). The column is free text, so a new kind needs no migration. Adding "start date changed", "estimate changed", or "moved from board X" is one row in each file plus one `recordCardChange(…)` call in the service that makes the change.
- **D742 — Recorded in the service, in the change's transaction.** `recordCardActivity` (and `recordCardChange`, `recordCardItems`, `recordSnapshotChanges`) run inside the transaction of create, patch, move, Bin, restore, archive, relations, attachments, and sprint completion. Every surface (web, MCP, REST v1, agents, approved proposals) goes through those services; `via` is read from the audit context they already set (`auditVia()`), so the history names the same surface as the audit log. A refused or failed change records nothing.
- **D743 — Coalescing.** `title`, `description`, `column`, `due`, `parent`, `level`, and `sprint` fold into the card's latest entry when it is the same kind, by the same person through the same surface, under two minutes old: first `from`, last `to`, the new time; dropped when they meet (dragging a card out and back leaves nothing). Item kinds (assignees, tags, flags, relations, files) never fold.
- **D744 — Retention.** History lives as long as the card: binning keeps it, purging (Bin, board purge, retention sweep) deletes it by the `card_id` cascade.
- **D745 — Reading.** `GET /cards/:k/activity` for any reader of the card, keyset pages on `(created_at, id)` in either order; MCP `get_card_activity` (`tasks:read`, so REST v1 too). A relation entry whose other card the reader cannot open (or the key may not read) has no id or title (T90, T203). Only the card's own files are recorded as added (a comment's files show in the comment); every removal is.
- **D746 — The timeline.** The Comments header gets an **Activity** switch and a **Newest first / Oldest first** button; both are saved per person in this browser (localStorage key `nook:card-timeline:<userId>`, like the Today sections and the Files view; `user_preferences` holds only module switches under a CAS revision and a 512-byte CHECK, not worth a migration for two display choices). Defaults: Activity on, oldest first (the comments' old order). Comments keep their look; activity rows are compact (icon, actor in bold, sentence with bold values, relative time with the absolute time on hover). The composer stays below. Nothing older than the newer of the two lists' loaded floors is shown, and **Load earlier** pages whichever list is behind (top when oldest first, bottom when newest first).

Not recorded (on purpose, for now): the fields a card is created with (the `created` entry stands for them), a binned card's subtasks (the root's `binned` entry has the count), tag renames and deletions on the board, comment edits and deletions, and a subtask's sprint (it follows its parent's and stores none).
