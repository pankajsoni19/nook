# Tasks views that work like boards (lane VIEWS)

Operator, 2026-10-23: "boards have capability to collapse columns. but views in tasks dont have that … views only have 3 columns … drag and drop dont work here … what i wanted was views to be same as boards in the functionality they offer … if view has only 1 board in it we can offer similar capability as the board, as it's essentially a board with filters. if needed we can place this sort of view inside board."

Decisions start at **D635** (D628–D634 are lanes CAP and COLICON's). Threats start at **T442**. Migration **077**. Slice 2 (lane VIEWS2) is D650–D669, T448–T450, migration 078.

## Why views fell short

- A view's board layout is `StateLanes` (`src/tasks/home/QueryResults.tsx`) over `stateLanes()` (`homeResults.ts`): always the three normalized states, To do, In progress, Done.
- Drag was deferred by D143 / Q9 ("Move to…" only); collapse was never wired; results are paged (50–100) and sorted by due or updated, not by board position.
- The board page already takes the same filter grammar in `?q=` (`boardUrl.ts`, `filterBoardCards` / `matchesQuery` in `shared/taskQuery.ts`), with collapse, drag, WIP limits, the composer, the card dialog, sprints, levels, and archive. A view over one board is "the board plus `?q=`".

## Slice 1 (this lane)

### 1. A single-board view is the real board

- **D635 — Board views.** A view whose canonical filter has exactly one positive `board:` term with one value (`scopedBoardId`) is a *board view*. `toView()` returns `board_id` (null otherwise, and null when the viewer cannot read that board, so they keep the cross-board page with its empty result). The board view renders the board engine (`BoardView`: board, table, list, calendar) with the view's terms minus that `board:` term (the in-memory matcher has no `card.board_id` to match). Everything the board offers works there: collapse, drag, WIP, the composer, the card dialog, sprints, levels, archive.
- **D636 — Board view URLs.** `/tasks/:b/views/:v` is the saved view on its board; a `?q=` (present, even empty) is an unsaved change to its filter; the board's own `view`, `group`, `sort`, `cal`, `month`, and `sprint` keys work as on the board. Its card is `/tasks/:b/views/:v/card/:k` (and `/full`), the Sprints sheet `/tasks/:b/views/:v/sprints`. Opening `/tasks/views/:v` for a board view replaces the entry with the board view (keeping an unsaved single-board `?q=` minus the board term, and the saved layout); a board view whose saved filter is no longer on that board (edited elsewhere to more boards) replaces back to `/tasks/views/:v`. A deep link's in-app Back from a board view goes to the views list. These are called **saved views** on the board, because the board's own `?view=` means the layout.
- **D637 — Sprints and new cards in a board view.** The sprint switcher defaults to **All** (`sprint=all`) in a board view, so the view's filter, including any `sprint:` term it has, decides what shows and the sprint-conflict note never fires for the view's own term; picking a sprint is explicit in the URL. **New card** is prefilled from the view's single-value positive terms (`column:`, `state:` → the first column of that state, `assignee:` (me, or a person already on the board), `tag:`, `flag:`, `sprint:`); a prefilled draft is not "dirty" until something changes. If the new card does not match the view, it is added and the toast says "Added — hidden by this view's filters".
- **D638 — The saved-view picker.** The board header has **View: All cards ▾**, listing All cards and the views pinned to this board that the viewer can read (theirs, shared with them, shared with everyone). The filter bar gets **Save view…** (a new private view: `board:<b>` plus the filter, the layout mapped to list/table/board, calendar keeps board) and, on an owned, editable, changed view, **Save** (PATCH with the revision; 409 `VIEW_CHANGED` offers a reload) and **Discard**. Rename, Share, Duplicate, and Delete are in the picker's **View options** (the same rules and dialogs as the view page, D140). Choosing a view pushes an entry.
- **D639 — Collapse in a board view** uses the board's own `board_view_prefs` (operator default: shared between the board and its views), so a column collapsed on the board is collapsed in every view of it.

### 2. Multi-board views: Columns lanes (default) and State lanes, both with drag

- **D640 — Columns lanes.** Lanes are the union of the columns of the boards that have matches, keyed by (folded name, state) (`shared/taskLanes.ts`, the same fold as text matching). One name in two states is two lanes, labelled "Review · Done" and "Review · In progress". Order: state (To do, In progress, Done), then the median of each column's relative position on its board (index ÷ (columns − 1)), then the name. Over **20** lanes the results fall back to State lanes with a notice ("Too many different columns to show side by side; showing state lanes"). The choice is saved with the view (`display.lanes: "columns" | "state"`, default columns) and is a URL key (`lanes=state`).
- **D641 — Drag between lanes.** A card dropped on a lane moves to **its own board's** column of that lane (to the top; `afterCardId: null`). The drop is refused, with the lane dimmed and the reason shown, when the card's board has no such column ("<Board> has no Review column"), when that column is at its WIP limit, or when the viewer cannot edit the card's board (those cards are not draggable at all). There is no reordering inside a lane (the cards come from many boards and the query's sort). `Alt` + ← / → moves a focused card to the previous or next lane that can take it. The move is optimistic and rolls back with a toast on any refusal from the server, which stays authoritative (edit level, 409 `COLUMN_FULL`, the done and archive clocks).
- **D642 — State lanes.** To do, In progress, Done; a drop goes to the first column of that state on the card's board (refused when it has none).
- **D643 — API.** `POST /api/tasks/query` and `GET /views/:v/cards` take `lanes: "columns" | "state"`. With it, the first page also returns `lanes` (the mode used: `state` after a fallback), `lanesFallback?`, `columns` (each lane's key, label, state, and its board columns with `wip_limit` and live `card_count`), and `laneCounts` (true counts per lane over the whole match, not the loaded page); and `limit` may go to 200. The board layout pages 200 at a time with **Load more**. My work uses the same lanes.

### 3. Collapse everywhere

- **D644 — `task_view_prefs`** (migration 077): `(user_id, view_key, collapsed_lanes JSON ≤ 1024 bytes, updated_at)`, `view_key` the view's id or `my` (My work). `GET` / `PUT /api/tasks/views/:v/prefs { collapsedLanes }` (a reader of the view; `my` for anyone), not audited. `PUT` keeps only well-formed lane keys (`s:<state>` or `c:<state>:<folded name>`), at most 40, deduplicated, trimmed to fit 1 KiB; for a saved view it also drops keys that are not lanes of the view's current results. Rows go with the view (deleted with it) and with the person. A collapsed lane is the board's 44 px strip and is still a drop target (to the top). An unsaved new view keeps collapse in memory.

### 4. MCP

- **D645.** `list_views` adds `board_id` (D635) and `lanes`. `move_card` takes exactly one of `columnId`, `state` (the first column of that state on the card's board), or `columnName` (the first column with that name, case- and accent-folded, on the card's board), so an agent can move a card the way a lane drop does without looking up column ids; a board without one is `INVALID` with reason `NO_SUCH_COLUMN`.

### 5. Phones (390 px)

- **D646.** A board view is the board's one-column pager with tabs. Multi-board lanes use the same pager and tabs (a collapsed lane keeps its page and says its cards are hidden). Drag is off on phones, as on boards; **Move to…** on a card lists the merged lanes (or states) and moves it like a drop, with the same refusals; "Other column on this board…" keeps the board's own sheet. Back and Forward step through the same entries as the desktop.

## Slice 2 (lane VIEWS2, as built)

Operator, 2026-10-23: "complete". Decisions **D650–D669**, threats **T448–T450**, migration **078** (`task_view_pins`; `board_view_prefs.show_all_levels`, `collapsed_rows`; `task_view_prefs.own_collapse`, `collapsed_columns`, `collapsed_rows`).

### 1. Lanes by a field across boards

- **D650 — Grouped lanes.** The board layout of a cross-board view (and My work) adds **Lanes: Assignee, Tag, Sprint, Due date, Board** to Columns and State (`display.lanes`, `lanes=<mode>` in the URL, `POST /api/tasks/query { lanes }`). Assignee: one lane per person on a matching card (a card with two people is in both), by name, then **No assignee**. Tag: tags merged across boards by folded name, by name, then **No tag**; each lane knows every board's tag of that name. Sprint: **Backlog** first, then every active or planned sprint of the boards with matches (so cards can be planned into an empty one) and completed sprints that still have matches, merged by folded name, active first, then planned in board order. Due date: Overdue, Today, This week, Later, No due date (the viewer's zone). Board: one lane per board. Counts are true counts over the whole match (a card counts in each person's or tag's lane). Over **20** lanes the results fall back to State lanes with the notice, as merged columns do. Grouped lanes show a person, tag colour, sprint, date, or board mark where a column has its status icon.
- **D651 — Drag between grouped lanes.** Cards can have several people and tags, so a drop **replaces the source lane's value with the target's**: from Asha's lane to Ben's, Asha comes off and Ben goes on (other people stay); from No assignee, Ben is added; onto No assignee (No tag), every person (tag) comes off, so the card lands where it was dropped. A tag lane uses the card's own board's tag of that name; a sprint lane plans the card in its own board's sprint of that name, and Backlog takes it out of its sprint. Refused, with the lane dimmed and the reason: below Can edit on the card's board, the board has no such tag or open sprint, the sprint is completed, sprints are off on the board, or the card is not at its board's work level (subtasks follow their parent). Due and Board lanes only show cards (no drag, no Alt+arrows; "Move to…" still lists the board's columns). The change is a `PATCH /cards/:k` with the card's revision; Alt+← / → and "Move to…" on phones do the same.
- **D652 — A failed move fetches again.** A lane move (column or field) that the server refuses no longer puts back a snapshot: the toast says why and the first page is fetched again behind the screen (as many cards as were loaded, up to the page cap), so a change that landed meanwhile shows at once.
- **D653 — Trimming collapsed lanes.** Collapsed grouped lanes (merged columns, people, tags, sprints, boards) stay only while they are lanes of the results: a saved view's own filter, and for My work the filter it sends with the change (`q`, run only when it has a positive `assignee:me`). State, due, and the none lanes always exist; a mode that fell back keeps its keys for when it fits again.
- **D654 — Add a card in lanes.** Each lane has **Add a card** when some board can take it: the boards with matches where the viewer can edit cards and the lane has a place (its column, or the first column of its state; its tag; an open sprint; any editable board for a person or the backlog; the board itself for a Board lane; none for due lanes). With more than one, a sheet asks which board; then that board's own composer opens on the lane's column, or with the person, tag, or sprint filled in. After it is created the results are fetched again.

### 2. Swimlanes on the board

- **D655 — Swimlanes.** The board layout (on the board and in a board view) has **Swimlanes: None, Assignee, <parent level>** (`?swim=assignee|parent`; parent only on a board with levels, named for the level above the work level, such as Epic). Rows are one per person (a card with two people is in both rows), by name, then No assignee; or one per parent in board order, then "No <level>". The column heads stick to the top and the row names to the left. A board view saves its swimlanes with the view (`display.swimlanes`) and opens in them; `swim=none` turns them off in the URL, and a different choice shows **Save** like a filter change.
- **D656 — Drag across rows; collapsed rows.** A card dropped in another row changes that field first (the source row's person replaced by the target's; the new parent, which must be one level up; No parent detaches), then moves to its place in the column (WIP refusals as on the board). Rows collapse per person: `board_view_prefs.collapsed_rows` (row keys `a:<user>`, `k:<card>`, `none:a`, `none:k`, at most 40 within 1 KiB; a parent row's key stays only while its card is live on the board). On phones the board's column pager stays, with the rows inside each page; drag is off there (the card's own fields change the row).

### 3. A board view's own collapse, pins, and widening

- **D657 — Keep this view's own collapsed columns.** In a board view's options, off by default (the view shares the board's collapsed columns, D639). Turned on, it starts from the board's collapsed columns and rows and keeps its own from then on (`task_view_prefs.own_collapse`, `collapsed_columns`, `collapsed_rows`, per person); collapsing there leaves the board as it is. Turned off, the view shows the board's again.
- **D658 — Pinned views.** The board's owner or a manager pins a view they own that is on that board (**Pin for everyone on this board**). Everyone who can open the board then reads it: the board's **View** picker lists it first under "Pinned for everyone". It runs as each viewer, so it shares only its name, filter, and layout; readers duplicate rather than edit. At most 20 per board; they, or the view's owner, unpin; the pin goes when the view's filter leaves the board, and with the view or the board. Audited.
- **D661 — Widening a board view.** A board view's filter bar has a **Board** field (first in + Filter): picking another board makes the view cross-board, and the page moves at once to its cross-board page with the change unsaved (this board and the others in one `board:` term; column filters, which need one board, are left out with a note). Save there keeps it.

### 4. Show all levels, MCP, and checks

- **D659 — Show all levels per person on the server.** `board_view_prefs.show_all_levels` (null until the person chooses), like collapsed columns and Show auto-archived cards. The per-device choice an older build kept is sent once when the server has none, then removed.
- **D660 — MCP `save_view`** (`tasks:write`): create a private view (name and filter) or change one the key's owner owns (`viewId` and `baseRevision` from `list_views`, which now returns `revision` and `layout`); `VIEW_CHANGED` with `currentRevision` when stale. Sharing and pinning stay app-only (D180). Only keys over the whole Tasks module see it (T449); chat agents are never offered it.
- **D662 — A real pointer drag.** `Input.dispatchMouseEvent` press, moves, and release in Chrome's new headless mode start real HTML5 drags (dragstart, dragenter, dragover, drop, dragend in Chrome's own input pipeline; no synthetic `DragEvent`). Checked on the QA instance: a swimlane drag that changed the person and the column; a cross-board drag between person lanes; a drop on a collapsed lane's strip (to Done); a drag across parent rows; a tag-lane drag that swapped the tag; and a refused drop (another board's tag) that changed nothing. `Input.setInterceptDrags` was not needed.

### 5. Leftovers done (operator: "complete", D663–D669)

- **D663 — Pinned views over MCP.** `list_views` also lists views pinned on boards the key's owner reads, and every view carries `pinned_board_ids` (only boards a key limited to chosen boards reaches; a key limited to chosen views still lists only those).
- **D664 — Swimlane cells.** Each cell of the board's swimlanes has **Add a card** (+): the composer opens on that column with the row's person, or under the row's parent. `Alt` + ↑ / ↓ moves a card up or down within its cell and, past the first or last card, into the row above or below (to that cell's bottom or top), changing the person or parent as a drop does; the first and last rows say so. `Alt` + ← / → still moves to the next column in the row.
- **D665 — Swimlanes across boards.** A cross-board view's (and My work's) lanes split into rows by **Assignee** or **Board** (`swim=assignee|board`, saved with the view as `display.swimlanes`; not the same field as the lanes). Rows come from the loaded cards. A drop in another lane does what a lane drop does; in another person's row it swaps the source row's person for the target's, both in one PATCH plus the move. Board rows only show (a card stays on its board). `Alt` + arrows move to the next lane or row that takes the card. On phones the lane pages group their cards under the rows.
- **D666 — Create the tag on drop.** A card dropped on a tag lane whose name its board has no tag for is no longer refused when the viewer can edit cards there: the lane says "Drop to create …", and the drop asks **Create tag “X” on <board> and move** (any reader may create tags; an existing tag of that name is used). Without edit it stays refused with the reason.
- **D667 — Reorder pinned views.** The board's owner or a manager reorders them (`PATCH /boards/:b/pins/:v { afterViewId }`, audited `task.view_pin_move`): **Move up** and **Move down** in a pinned view's options, and **Reorder pinned views…**, a sheet to drag them or use the arrows.
- **D668 — `scripts/dragSmoke.ts`.** The real pointer drags (D662) as a script against a QA instance: it signs in as the QA account, makes its own boards, cards, tags, and view, checks six drags through the API (a person lane to No assignee, a collapsed Done strip, board swimlane rows and columns, tag to tag, a tag created on drop, and cross-board rows and lanes), cleans up, and exits 1 on a failure. Run it before a release (docs/OPERATIONS.md).
- **D669 — Folded rows across boards.** A cross-board view's and My work's folded swimlanes are kept in `task_view_prefs.collapsed_rows` (well formed and bounded; board views still trim theirs to their board). No migration.
