Full-text search

The search box at the top of the note list searches the text of your notes, not just their titles.

Syntax

Every word must appear, in any order; case and accents are ignored, so creme finds “Crème”. The last word matches as a prefix while you type; end with a space for whole words. "double quotes" match an exact phrase. AND, OR, NOT, *, and title: are ordinary text. Link text, image descriptions, and code are searched; link addresses are not.

What you see

Your own notes are searched as last saved, including drafts marked Draft. Shared notes are searched as their latest published version; you never see someone else's draft. Binned notes are not searched. Title matches rank first, with a highlighted excerpt, folder, owner, and last edit.

Scope

Search covers the section you are in: All notes, Shared with me, or one folder. Search all notes widens it; opening a result from outside the section switches to All notes.

  • Ctrl+K (⌘K on a Mac) or / focuses search; Esc clears it; ↑/↓ and Enter pick a result.
  • On phones, Back from a note returns to the results with the query kept. The query lives in the tab's history state, never in the URL.
  • Up to 20 searches per 10 seconds per user (then title matches only, with a notice) and 200 characters per query. Files are not searched yet.

Using Nook

Task boards

New board asks for a name and a template: Simple kanban, Personal to-do, Task checklist, Scrum sprint board, Epic › Story › Subtask, Bug triage, or Content pipeline. Boards start private; share one with people and groups, or everyone signed in, from the Access sheet.

Cards

New card opens a composer that sets the title, column, due date and time, assignees (up to 20), description, relations, and attachments in one step. Drag cards between columns, or use ⋯ → Move to… and Alt+arrows. Open a card over its board or as a full page.

Tags, flags, relations

Up to 10 colour tags per card from the board's tags, four flags (Urgent, Blocked, Needs review, On hold), and relations to cards on any board you can open: depends on, needed by, relates to, duplicates. A card you cannot open shows as restricted.

Columns

The owner sets each column's state (To do, In progress, Done) and an optional WIP limit; a full column refuses new cards. An icon left of each name shows the state, from a dashed Backlog circle through filling In progress circles to a green Done check. Done columns count as finished everywhere, and cards that sit in one for 30 days (or the board's own number) are archived: hidden, never deleted, and restored in one click; Archive in a card's menu hides one by hand, with Undo. Anyone can collapse a column to a narrow strip, just for them.

Four views

Columns, a sortable Table, a List grouped by column, assignee, tag, flag, parent, or due date, and a Calendar where you drag cards to reschedule, with an Unscheduled tray.

Filters

+ Filter adds Assignee, Tag, Flag, Due, Column, Level, Parent, Sprint, or Relations; the text box matches titles and descriptions. The view, filters, and sort live in the URL, so a filtered view is a shareable link.

Who can do what

Each person or group has a level: Can edit (the default) adds, edits, moves, and comments on cards; Can comment only comments; Can view only reads; a Manager also changes columns, structure, tags, sprints, and sharing up to Can edit. Only the owner deletes the board. Viewers and guests only read.

Subtasks, epics, and sprints

A board starts flat. In Board settings → Structure the owner picks Task › Subtask, Sprint › Task, Sprint › Task › Subtask, Epic › Story › Subtask, or custom names for up to three levels, and which level the columns show.

Subtasks

A card lists its children as a checklist with a count such as 2/5 and a progress bar. Add subtask… adds one on Enter; ticking one moves it to the first done column. When the last is done, Nook offers to move the parent too.

Parents

A card below the top level has a parent field (Epic, Story, or Task). Drag a card onto one a level up, or use ⋯ → Set epic… on a phone. The table shows cards as a tree; the Bin keeps a tree together.

Sprints

On a sprint board, a switcher shows the active sprint, planned ones, Backlog, and All cards, with a strip of days left and done counts. The owner adds, starts, and Complete…s sprints, choosing where unfinished cards go.

My work and saved views

The top of Tasks has three segments with their own addresses: Boards, My work, and Views.

My work

Every card assigned to you on any board you can open, grouped by Overdue, Today, This week, Later, and No due date. Pick Open, To do, In progress, Done, or All; add filters; switch between a list, a table, and columns; and Save as view.

Views

A view is a saved cross-board filter and layout. Share it privately, with selected people, or with everyone; recipients read it and can Duplicate it. A view never widens access: each person sees only cards on boards they can open.

A view on one board is the board

When a view names exactly one board, it opens as that board with the view's filters: the same columns, collapse, drag, WIP limits, New card (started with what the view asks for), and sprints. On any board, View: All cards ▾ lists the views on it, and Save view… keeps the filters on screen as one.

Lanes across boards

The columns layout of a view or My work merges the boards' columns by name (Lanes: Columns) or shows To do, In progress, and Done (Lanes: State), with true counts. Drag a card to another lane to move it to that column on its own board; a lane that can't take it says why. Collapse any lane; on a phone the lanes are pages with tabs.

Whiteboards

Boards drawn with the Excalidraw editor at /whiteboards, each saved as a .excalidraw file in one of your folders, so Files lists them too.

  • New names a board and picks a folder. Drawing saves on its own a moment after you stop; the bar says Saved, Saving…, or Offline, kept on this device, and unsaved work waits on the device until it can be saved.
  • If the same board changed on another device, Nook asks whether to Reload latest or Save mine as a copy; nothing is overwritten silently.
  • ⋯ shares the board through the Access sheet (people you share with can view; only you edit), renames, moves, downloads the .excalidraw file, exports a PNG, or moves it to the Bin for 30 days.

  • Links: select a shape and link it to a note, file, board, card, collection, event, or another whiteboard; Back returns to the board where you were. Web links open in a new tab after Nook shows the full address.
  • History (⋯) keeps a version every 30 minutes while you draw and whenever you empty a board, up to 20; restore one or save it as a copy. Duplicate, Import a .excalidraw file (its pictures become files), and Export SVG are there too.
  • Type /whiteboard in a note, or paste a board's link alone on a line, to show it as a card; search finds boards by their text with the Whiteboards chip.

Vault

Team secrets (API keys, database URLs, service passwords, certificates) with a value per environment: dev, staging, prod, or names you choose. The Vault appears once an admin has set the server's vault key; guests never see it.

Encrypted at rest; anyone with the server and its key can read every secret. It is a secrets manager for your own services, not a personal password manager: no browser extension or autofill. Names, environment names, and tags are not encrypted.

Secrets and environments

A secret is a Value, a Login (username, password, URL), or a Note, with an encrypted comment and tags. On a computer a vault is a grid of secrets by environment; on a phone you pick the environment and each secret is a card.

Reveal, copy, generate

Reveal hides again after 30 seconds; Copy clears the clipboard after 30 seconds. Generate makes characters, a hex or base64url token, or a passphrase in your browser. Also save in writes one value to several environments.

Access per environment

People and groups get No access, Read, Write, or Admin on each environment; Owners hold everything. Admins get no access to a vault they are not in. Removing someone starts a new data key and reminds you to rotate what they could read.

Protected environments

Prod starts protected: seeing, copying, or exporting its values asks you to confirm it's you, which opens protected environments for 15 minutes on that device. Writing needs only write access.

History, import, export

The last 20 versions per value, with Restore. Import reads a .env, JSON, or CSV file in the browser and previews every change; Export downloads one environment (10 an hour, recorded).

Activity and keys

Activity lists who revealed, changed, imported, exported, or shared what, never a value. nkv_ vault keys let scripts, CI, and AI clients read and write secrets over REST and MCP. Edit a key to add a vault or an environment, raise read to write, or turn its settings on, after your password; the key keeps its secret, and you get a security email and a bell notice.

Chat and agents

Chat (/chat) is where you talk to agents: a prompt, a model, a step limit, and the tools you pick, made in Settings → Agents. Chat appears once an admin has set the server's key and added a model provider; guests never see it.

Every message leaves this Nook. Your messages, the agent's prompt, and every reply go to the model provider's endpoint an admin configured; the composer says so.

Chatting

Chats are grouped Pinned, Today, Yesterday, and by date, with search. While the agent answers, Send becomes Stop; an answer keeps going when you leave and resumes when you return. Edit and Regenerate keep every version behind a ‹ 2 / 2 › switcher.

Images

Attach up to 5 PNG, JPEG, GIF, or WebP images per message (paste, drop, camera, or From Files), sent only to models an admin marked as able to see images. Replies render GitHub Markdown; pictures from other sites load only when you ask.

Tools

An agent may call tools from MCP tool servers an admin added. A reply shows Used N tools with each call. A tool that is not read-only asks first with Deny and Allow once; nothing runs until you answer.

Nook's own tools

Agents read what you can read in Nook, and a change they want to make becomes a proposal in your Inbox. Link one of your own API keys to narrow what an agent reaches; direct writes are opt-in and still ask first.

Data sources

When an admin opens a report data source to chat agents, an agent can search its schema and run guarded SELECTs. Results show as a table with its SQL, CSV, and Turn into a report. Never over API keys or MCP.

Sharing and audit

Share an agent (Can view to chat, Manager to edit) or a chat read-only; recipients continue in a copy of their own. Admins may allow public snapshot links. Runs through API keys and MCP appear in the Audit log, never as chats.

A daily token budget per person (and optionally for the whole Nook) shows under the composer as a percentage and resets at midnight UTC. Agents and chats moved to the Bin wait 30 days. Agents can also search knowledge bases.

Knowledge

A knowledge base is a set of texts your agents can search: published notes, .txt, .md, or .csv files (1 MiB each), and pasted text, up to 500 sources. Make one in Settings → Knowledge (/settings/knowledge; not for guests).

How it searches

Pick a model provider that makes embeddings for search by meaning, or Keyword search (no embeddings), which sends nothing to a provider. On Local embeddings the text is embedded on the Nook server itself, with no token cost.

Sources

Each source shows Waiting, Paused, Indexing, Ready, Error, or Unavailable. A published note is indexed again a minute after you publish it; a note or file its owner can no longer read leaves the base at once.

Try it

Searches the base the way an agent would and shows the top passages with their heading paths and scores. Re-index all (once an hour) and Change embedding model move a base to another model or back to keywords.

In an agent

Tick bases you own or manage in the agent editor's Tools. They become one read-only tool, search_knowledge, that never asks first; a reply shows Searched knowledge with the passages it found. Keys with Read agents, chats, and knowledge can search over MCP and REST.

Sharing

Can view lets people search a base; Manager also adds and removes sources, re-indexes, and attaches it to agents. Only the owner moves it to the Bin.

Anyone who can use an agent with this knowledge base can read its text. With an outside provider, the whole text is sent to it when indexed, and the passages an agent finds go with the agent's answer.
Using Nook

Reports

Analytics reports over ClickHouse: SQL and charts over the warehouse tables an admin allowed, written by the AI from your docs. Queries run on that warehouse, never on your notes.

Data sources

Admins add ClickHouse in Settings → Report data sources, with Test connection, an allowlist of databases, and a schema catalog the AI and the Schema browser read.

Generated from docs

New report takes up to 8 docs: Nook notes and files (PDFs too) and docs behind a tool server such as Outline. The AI plans, runs queries to check its numbers, and holds them to the metrics the docs define.

SQL guard

Every query must be a single SELECT on allowlisted tables, with no table functions, and runs read-only with a row limit and timeouts. Filter values are bound as typed parameters, never pasted into SQL.

Charts

KPI, line, bar, pie, scatter, table, heatmap, calendar, funnel, gauge, treemap, sankey, boxplot, histogram, waterfall, combo, and bullet, with stacks and small multiples, laid out for phones and desktops.

Inspect and Edit SQL

Inspect on a block shows its SQL, the mapping, and where it came from in the doc. Owners Edit SQL with a preview; people at comment level Suggest an edit. The SQL console runs saved queries with parameters.

Changes

Comment on a report or a block in plain words, or Add a new section; the AI answers with a proposal you apply or reject. Each applied change is a numbered version you can compare and restore. A trash icon deletes a section, with Undo.

Filters

Date ranges with presets in the report's time zone, filters drawn from the data, number and text inputs, linked filters, exclude, and saved views. Values live in the URL; Click to filter on a chart; owners add filters with + Filter (lists, text contains, date and number ranges) and remove them from the filter itself.

Refresh and schedules

Refresh all or one block, or schedule hourly, daily, weekdays, or weekly. Runs keeps each refresh, generation, and change with its step log; results are cached per set of filter values.

Organize and share

One shared folder tree, ★ Favorites, and Lists of reports from any folder. Several owners per report; share with people and groups (view or comment) or everyone. Duplicate report makes your own copy.

Agents and keys with the reports permission list, read, create, refresh, and comment on reports over MCP. Admins recover reports nobody can manage in Settings → Report owners, and set a separate report model and a fallback model in Settings → AI. Chat agents can query a data source an admin opens to them (see Chat and agents).

Bin

Deleted notes, files, cards, boards, collections, rows, calendars, and events stay in the shared Bin (the Bin button in the account row, or /bin) for exactly 30 days. Retention is fixed.

  • The Bin lists your own deleted items, newest first, with the days left; filter by kind. A card binned by someone else on your board is listed for you (the owner) and for them.
  • Everything is kept: drafts, versions, file bytes, and sharing. Nobody can read a binned item, including MCP clients.
  • A card moves to the Bin with its subtasks as one item (“+ N subitems”), and one restore brings the tree back.
  • Restore returns a note or file to its original folder (or Default if that folder is gone; the toast names the folder and any sharing that returns) and a card to the bottom of its column (or the board's first column). An item inside a binned board or collection can be restored only after its container.
  • Blank notes that were never published skip the Bin.
  • Delete forever and Empty Bin remove items permanently. An hourly sweeper, also run at boot, removes expired items.
  • Binned files still count towards the storage quota.
Using Nook

Team

Team (the Team button next to Bin, or /team) lists everyone with an account and their team role. Admins also open it from Settings → Manage team.

Roles

An Admin can do everything a member can and manages the team; a Member works as before. The first account on a new Nook is the admin; on upgrade, the oldest account becomes the admin. A Viewer reads everything shared with them or with everyone and changes nothing; a Guest reads only what is shared with them by name. Viewers and guests see a View only banner and no create, edit, share, or upload controls; viewers' MCP keys only read and guests have none. New accounts are guests unless SIGNUP_ROLE says otherwise. Nook always keeps at least one admin.

Blocking

Block signs a person out on every device and stops them signing in; MCP keys and calendar links pause, and their content stays shared. Unblock restores access with their existing password. Admins can also sign an account out everywhere without blocking it.

Privacy

Everyone sees names and roles. Only admins see emails, last seen, two-factor status, storage, and the activity log; nobody sees anyone else's private content. Admin changes ask for your password and a fresh code.

Groups

Admins create groups in Team → Groups and decide who is in them; owners share items with a group at a level, and everyone in it follows as people join or leave. A group opens nothing by itself, admins adding themselves is flagged, and guests in a group only read.

Central access

Open a member’s Access page to see everything they can reach and through what, with titles hidden for items you cannot open. Admins only take access away (remove, lower, leave a group, revoke keys, or Reset access), and the owner hears about it. Templates give invites a role and groups; Access activity logs every change; everyone but guests sees their own in Settings → My access.

Invite links

Admins open Team → Invites and create a single-use link with a fixed role (member, viewer, or guest) that expires in 1 to 7 days, optionally bound to one email address. The link is shown once, can be revoked, and works even while registration is closed; ALLOWED_EMAILS still applies. With email set up (Resend), Nook can also send the link to the bound address.

Using Nook

Inbox

The Inbox (the button next to the bell, or /inbox) collects changes your MCP keys suggest instead of making. Nothing changes until you approve it, and only you see your keys' suggestions.

Proposals

A key with Suggest changes (inbox:write) plus a module's read permission proposes cards, card changes and comments, events, rows, and note drafts with submit_proposals. Each one shows the agent's reason as plain text, what it changes, and a before-and-after table or a line diff.

Approve or reject

Approve applies the change as you, with your access; if the item changed since the agent read it, the proposal fails and nothing is applied. Reject takes an optional reason the agent can read. Approve all works one proposal at a time.

Today and the bell

Proposals awaiting you on Today replaces Drafts from agents. The bell says which key suggested how many changes; push for proposals is off until you turn it on. Proposals expire after 14 days.

Using Nook

Routines

A routine is a prompt you keep in Nook (Inbox → Routines, /inbox/routines) for an agent to run on a schedule. Nook only says when it is due; your MCP client runs it, and everything it suggests waits in the Inbox.

Set it up

Name, instructions, the kinds of change it may suggest, optional boards, calendars, collections, or folders it is pinned to, a schedule (daily, weekdays, weekly, hourly, or manual) in your time zone, an optional bound key, and a per-run limit (25 by default). Nook enforces the kinds, pins, and limit.

Run it

A client calls list_due_routines, start_run (a two-hour lease), submit_proposals with the runId, and finish_run with a summary. In Claude Desktop each routine is also a routine.<name> prompt. A run left open is marked abandoned and the routine stays due.

Review it

Proposals are grouped by run with its summary; the bell says "Weekly review suggested 4 changes" once per run. Each routine keeps its last runs with status, proposal and tool-call counts (counted by Nook), and duration.

Using Nook

Notifications and email

The bell (and /notifications) collects reminders, proposals, and changes that involve you. Push and email are set in Settings → Notifications (/settings/notifications).

Push

On an HTTPS origin, turn on push for this device. Pushes carry no content. Turning off the Notifications module hides the bell; reminders and pushes still arrive.

Email

When an admin has set up email: assigned to you, comments on your cards, shared with you by name, and proposals awaiting you, each with its own switch. Emails of one kind are grouped, and nothing you do yourself emails you.

Digest and reminders

An optional Daily or Weekly summary at your local time, reminders by email, sprint and Bin clean-up emails (off by default), quiet hours, and muting per board or calendar.

  • Verify your address first; until then Nook sends only security emails. Security emails (new keys, role changes, two-factor, password, a sign-in from a new device) are always on.
  • Every activity, reminder, and digest email has a one-click unsubscribe for that kind. Emails link straight into the app and carry no images, trackers, or remote content.
  • Admins see what Nook sent, held, skipped, or failed in Team → Email log, never addresses, subjects, or content.
Using Nook

Settings → Modules

Each module has a switch, and every module is on until you turn it off. The choice is saved to your account, so it follows you to every device.

  • Notes, Files, Tasks, Collections, and Calendar: turning one off removes its tile and Today sections; its links go to Home with a Turn on in Settings hint.
  • Whiteboards, Vault, Chat, and Reports: turning one off removes its tile and its pages. Vault and Chat are hidden for guests, and for everyone but admins while the server has no key for them.
  • Search, Bin, Notifications, Inbox, and Team hide their boxes, buttons, and pages. Deleting still uses the Bin, reminders still arrive, agents can still suggest changes, and roles still apply.
  • Back steps over pages of a module that is off, and Forward stops before them until you turn it back on.
Hiding is not a security boundary. Nothing is deleted, sharing is unchanged, and MCP keys and feed links keep working. Revoke a key or link to stop it.
Using Nook

MCP server

An authenticated Model Context Protocol endpoint over Streamable HTTP lets trusted AI clients read your workspace and, with the permissions you grant, write drafts, cards, rows, and events.

1

Create a key

Open Settings → API keys (/settings/keys), choose New key, and build its access one permission at a time (module, permission, all or chosen items) with an expiry. It is shown in full only once; Nook stores its SHA-256 hash and a short prefix, never the plaintext. Viewers can create read-only keys; guests cannot create keys.

2

Configure the client

Copy the ready-to-paste configuration. The endpoint is <your origin>/mcp and the key is sent as a bearer token:

{
  "mcpServers": {
    "nook": {
      "type": "streamable-http",
      "url": "http://localhost:2026/mcp",
      "headers": { "Authorization": "Bearer <YOUR_API_KEY>" }
    }
  }
}
3

Revoke when done

Use a separate key per client, treat keys like passwords, and revoke unused keys from the same screen.

files:read, files:writeList, search (names and text, PDFs included), and read files: text files up to 1 MiB and the text of PDFs up to 16 MiB (attached PDFs too, through read_attachment_text; a scanned PDF has no text layer, and there is no OCR); store text files, upload files through a one-time ticket, rename and move your own files, and create folders. REST API

A key whose surface includes REST calls the same tools over HTTPS: GET /api/v1/me, GET /api/v1/tools, and POST /api/v1/tools/<name> with a JSON body. Send the key only in the Authorization header; a key in a URL is refused.

curl -s -X POST "https://<your nook>/api/v1/tools/list_boards" \
  -H "Authorization: Bearer <YOUR_API_KEY>" \
  -H "Content-Type: application/json" -d '{}'

A key limited to chosen items (folders, notes, files, boards, views, collections, calendars, routines, whiteboards) sees only those in every tool, list, search, and Today section. Behind a reverse proxy with TRUSTED_PROXY_HOPS set, a key can also be limited to IP addresses.

Only what you can open. A key sees exactly what its owner may read, never anything in the Bin, and restricted items only as “restricted”. Each key is rate limited per minute and per day, and writes are recorded in the audit log with the key's id.

Self-hosting

Vault key

The Vault is off until VAULT_ENCRYPTION_KEY is set. Values are encrypted with AES-256-GCM under a data key per vault, and the data keys are wrapped by this one server key.

openssl rand -base64 32

Set it in .env, or put it in a root-only file (or a Docker secret) and set VAULT_ENCRYPTION_KEY_FILE to its absolute path; not both. Nook refuses to start when the key is malformed, equal to TOTP_ENCRYPTION_KEY, or in a file inside the data directory. Check a key against the stored vaults (it prints counts only):

docker compose exec app bun server/vault-admin.ts verify-key
Keep the key away from the backups, and never lose it. A backup holds only ciphertext and wrapped keys, but a backup together with the key reveals every secret. Without the key there is no recovery: restoring a backup needs the key the vaults were made with. vault-admin.ts rotate-kek replaces the key with the app stopped; see docs/OPERATIONS.md → Vault.
Access

Accounts and sharing

Adding users

Add trusted addresses to ALLOWED_EMAILS, temporarily set ALLOW_REGISTRATION=true, restart, and let each person register. Disable registration afterward. New accounts get SIGNUP_ROLE (default member; viewer or guest also allowed) until an admin changes their role in Team.

Admins and recovery

Admins manage roles and blocks in the Team app. If the only admin was blocked or is no longer on ALLOWED_EMAILS, promote another account or unblock one on the host: docker compose exec mynotes bun server/team-admin.ts set-role user@example.com admin (or unblock, or list). The CLI cannot set a password: a forgotten password needs Forgot password? (with email on) or another admin account.

Google sign-in

Optional. Set AUTH_METHODS to google or both with an OAuth client whose redirect URI is APP_ORIGIN/api/auth/google/callback. Accounts are created automatically when registration would allow it (the first account, an invite, or open registration); GOOGLE_ALLOWED_DOMAINS keeps it to your company domains, two-factor still applies, and Google profile pictures replace the letter avatars, served by Nook itself.

Permission precedence

Everything is private by default. Folder access applies to inherited items, but an item's own sharing always wins. A person's level is the highest of their direct share, their groups, and everyone signed in, and their team role caps it. Nothing becomes public.

Authentication

Two-factor authentication

Users enroll under Settings → Security. The grouped setup key is entered once in an authenticator app. Sign-in uses the current six-digit code or one complete recovery code.

Recovery codes are encrypted. Viewing or replacing them requires a password and fresh TOTP code. Each works once.

Administrator reset

docker compose exec app bun server/reset-totp.ts user@example.com

This revokes the user’s sessions and requires fresh enrollment.

File names live only in SQLite; bytes are stored under server-generated ids. Uploads stream to .staging on the data volume, and a sweeper removes abandoned staging files at boot and hourly. The data directory is mode 0700; database and Markdown files are 0600; symlinks are refused.

Automatic migrations

Numbered migrations run transactionally before traffic is accepted and are recorded in schema_migrations. Released migrations are append-only.

One instance per data directory. Upload slots, locks, rate limits, and the sweeper live in the process. Never point a second container or a dev server at the same directory.
Operations

Backup and restore

Nook backs itself up while it runs: on the schedule in .env it snapshots the database (VACUUM INTO, checked with integrity_check), packs the data directory into a .tar.gz with a SHA-256 manifest, reads it back, and keeps the newest BACKUP_KEEP on this server's disk, in S3, or both. Litestream can add continuous copies of the database for a restore to any point in time, and restore drills check that a backup really restores. Admins see all of it in Settings → Backups, with Back up now and Run restore drill.

BACKUP_INTERVAL=6h
BACKUP_KEEP=14
BACKUP_TARGET=both          # local, s3, or both
BACKUP_DRILL_INTERVAL=7d
LITESTREAM_ENABLED=true     # needs an S3 bucket

By hand

./scripts/backup.sh                     # online, inside the running container
./scripts/backup.sh --offline           # stop, tar DATA_DIR, start (before upgrades)
docker compose exec app bun server/backup-admin.ts list
docker compose exec app bun server/backup-admin.ts restore-drill

Restore into an empty directory

docker compose stop app
MYNOTES_DATA_DIR=/srv/mynotes-restored docker compose run --rm app \
  bun server/backup-admin.ts restore --from latest --to /data
# or to a point in time, with the files from an archive:
#   --from litestream@2026-10-22T09:30:00Z --files-from latest
MYNOTES_DATA_DIR=/srv/mynotes-restored docker compose up -d
  • An archive is a plain tar.gz of a data directory: tar -xzf into an empty folder works too.
  • With STORAGE_BACKEND=s3 archives hold the database and the data directory, not the bucket's objects: keep bucket versioning on.
  • Retention deletes only nook-backup-*.tar.gz names in the backup folder or prefix, never anything else.
  • Keys are never in an archive. Keep .env apart from the backups, and the same keys for a restore.
  • After a real disaster restore with S3 storage, run storage-admin.ts reclaim once; a restore test uses another prefix.
Store .env separately. Backups intentionally exclude it and its keys; an archive together with the vault key reveals every vault secret.
Networking

Network and HTTPS

Compose publishes port 2026 for LAN access. Prefer Tailscale Serve or a TLS reverse proxy for HTTPS.

APP_ORIGINS=http://localhost:2026,http://<server-lan-ip>:2026,https://your-device.your-tailnet.ts.net
  • Use HTTPS for non-local access.
  • Set APP_ORIGINS to a comma-separated list of exact trusted origins; never a wildcard.
  • Keep COOKIE_SECURE=true with HTTPS.
  • Plain HTTP requires COOKIE_SECURE=false and is less safe.
  • Never serve the data directory as static content.
Security

Security model

Application

Argon2id passwords, opaque HttpOnly sessions, SameSite cookies, CSRF tokens, CSP, and authorised reads for every note, file, search result, and MCP call.

Data

AES-256-GCM TOTP data, hashed API keys, restrictive permissions, symlink refusal, atomic writes, and mutation locks.

Container

Non-root UID, read-only root, dropped capabilities, no-new-privileges, and a small tmpfs.

Supported shape: a single Docker Compose host using local SQLite/WAL storage. Rate limiting is in memory and does not coordinate across replicas.

Troubleshooting

Container cannot write data

Ensure the host path exists and is writable by UID/GID 1000.

Login fails behind a proxy, Tailscale, or LAN address

Add the exact scheme, host, and port to APP_ORIGINS. Plain HTTP also needs COOKIE_SECURE=false; prefer HTTPS.

TOTP code is rejected

Synchronize phone and server clocks. Codes are one-time; use a fresh code or recovery code.

An upload is refused

The message names the limit: file size (MAX_UPLOAD_BYTES), your quota (USER_STORAGE_QUOTA_BYTES, which includes the Bin), or free disk space (MIN_FREE_DISK_BYTES).
