Release notes

What's new in Nook

Every release, newest first. The full changelog, with fixes and development notes, is CHANGELOG.md; upgrade steps for each release are in docs/OPERATIONS.md.

What's new in v0.40.0

Interactive reports, and charts that fit the data.

  • Interactive reports: a date range (presets in the report's time zone, such as "Last 30 days (IST)", and a custom range), filters drawn from the data (such as Route), and number and text inputs.
  • Changing a value re-runs the report, with values bound safely as typed ClickHouse parameters. Values live in the URL, so links and Back and Forward keep them.
  • Anyone who can read the report can use them, and results are cached per set of values. Inspect shows the bound values, and MCP accepts parameter values.
  • The AI adds parameters from the doc, and Changes can add, update or remove them.
  • Smarter chart choice: a data-shape advisor suggests the chart kinds that fit each query, with a kind check against each block's intent and five new eval cases (funnel, cohort heatmap, quota gauge, latency spread, plan flow sankey).
  • New setting: REPORT_TIME_ZONE, the zone date presets resolve in for a report without a schedule.
Before upgrading: migration 063 runs on the first boot (new tables plus one column; nothing is rewritten), so back up first (./scripts/backup.sh --force). REPORT_TIME_ZONE is optional: a report uses its schedule's zone, then this setting, then the server's zone.

What's new in v0.24.0

Vault API keys: a separate key kind for scripts, CI, and AI clients, over REST and MCP, with an independent security review of the whole Vault.

  • Vault keys (nkv_). Settings → API keys → Kind: Vault key, for vaults and environments you can reach, at read or write. A vault key never reaches other modules and a general key never reaches the Vault. Its rights are always yours at that moment.
  • Protected environments over keys. "Every environment" never includes a protected one; a key reaches it only when the grant names it and the key allows protected environments. Protect an environment later and keys that did not name it lose it.
  • REST and MCP. /api/v1/vault/* for vaults, secrets, values with expectedVersion, and version metadata. MCP shows vault keys only the vault tools; values reach an MCP client only with "Allow MCP clients to read values".
  • Limits and alerts. Per key: 20 reads a minute, 1,000 an hour, 10 writes a minute, 200 a day, 60 values an hour over MCP. A limit hit, or more than 500 values in a day, shows in your bell and in Activity.
  • Where keys show. Keys with access on the vault's Access page, key:<name> actors in Activity, and a Kind filter in Team → Keys that shows vault keys as counts only.
  • Independent review. The whole Vault had an independent security review before this release: no HIGH finding, every MEDIUM fixed.

What's new in v0.20.0

The Vault: your services' secrets per environment, encrypted at rest, owner-only in this first release.

  • Vault. A new app for your services' secrets with environments (dev, staging, prod, or your own). Each secret holds one value per environment, an encrypted comment, twenty kept versions, and the Bin. A secrets × environments grid on a computer; one environment's cards on a phone. Values stay masked until Reveal and hide again after 30 seconds, when the tab is hidden, or when the dialog closes; Copy clears the clipboard after 30 seconds unless you copied something else since. A generator makes passwords, tokens, and six-word passphrases in the browser. Saving into several environments at once checks every environment's version.
  • Encrypted at rest; anyone with the server and its key can read every secret. The Vault is for your services' credentials, not a personal password manager. Values and comments use AES-256-GCM under a per-vault data key wrapped by VAULT_ENCRYPTION_KEY; names and tags stay plain for search.
  • Off until you set a key. VAULT_ENCRYPTION_KEY (openssl rand -base64 32, different from the TOTP key) or VAULT_ENCRYPTION_KEY_FILE outside the data directory, so backups never contain it. verify-key checks it; rotate-kek re-wraps under a new key read from a file, refuses while a server runs, and prints fingerprints, never the key.
  • Owner-only for now. Another member, a viewer, a guest, or an admin who does not own a vault gets "not found" everywhere. Sharing per environment, import and export, nkv_ API keys, and MCP tools follow in the next two releases.
  • Also. SQLite runs with secure_delete on for every module, and the server keeps a server.heartbeat file in the data directory while it runs.
  • For developers using MCP. No new tools; no key can reach the Vault yet.
Upgrading: back up first with ./scripts/backup.sh --force; migration 031 runs on the first boot and only adds tables. The Vault stays off until you set VAULT_ENCRYPTION_KEY. See Upgrading.

What's new in v0.18.0

API keys limited to chosen items in every module, a REST API for scripts and CI, address limits for keys, and a batch of small fixes.

  • Keys limited to chosen items in every module. An API key can now be limited to chosen folders and notes, folders and files, boards and saved views (only views you own, read only), collections, calendars, routines, and whiteboards. Every tool checks each item it touches: anything outside the key's choice answers "not found" as if it did not exist, and lists, search, Today, and counts include only the chosen items.
  • A REST API for keys. Scripts and CI jobs can call the same tools as MCP over plain HTTPS: GET /api/v1/me, GET /api/v1/tools, and POST /api/v1/tools/<name> with a JSON body of the tool's arguments. The tools, arguments, results, limits, and rules are the same as over MCP. Send the key only as Authorization: Bearer <key>; a key in a URL is refused. Every error has a stable code (AUTH_REQUIRED, KEY_INVALID, KEY_POLICY, IP_NOT_ALLOWED, KEY_IN_URL, NOT_FOUND, RATE_LIMITED, and for file uploads UPLOAD_NOT_FOUND, UPLOAD_CONFLICT, and UPLOAD_FAILED). See MCP server.
  • Where a key is used. Each key works over MCP (the default), REST, or both. Editing a key can only narrow this, without a password; to widen it, rotate the key or create a new one. Per-minute limits and "last used" are kept for each surface. Admins decide which team roles may use REST and MCP in Team → Policies (REST: admins and members by default).
  • Address limits for keys. A key can be limited to up to ten IPv4 or IPv6 addresses or ranges, offered only when TRUSTED_PROXY_HOPS is 1 or more. A refused call shows on the owner's key row and in its Recent activity section, with a shortened address; admins see it in Team → Access activity, without the address.
  • Rotating can change access. Because rotating asks for your password, it can now also change the new key's access, where it is used, and its allowed addresses, including widening them. Edit still only narrows, for example from all boards to chosen ones.
  • New optional setting TRUSTED_PROXY_ADDRESSES. The addresses or ranges your reverse proxy connects from; when set, forwarding headers are read only from those proxies. Set it as soon as TRUSTED_PROXY_HOPS is 1 or more; otherwise Nook logs a warning at startup and the app port must be reachable only through the proxy (for example "127.0.0.1:2026:2026" in compose.yaml). See Environment variables.
  • Small fixes. On a computer the Team pages and the Inbox scroll the list and the details separately; the Home header stays in place while Today scrolls; member pages no longer log a console error while Google sign-in is off; Back after deleting a note or file from its list no longer takes an extra step; the Publish version button is larger on phones; End, Home, PageDown, and PageUp scroll the Files list and long notes; an open Access sheet stops offering guests once sharing with guests is turned off; and Access activity lines read as sentences.
  • For developers using MCP. No new tools, and no tool on either surface deletes forever, shares, or manages keys.
